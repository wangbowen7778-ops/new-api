## 渠道亲和性：为「无会话标识」的请求增加内容哈希键源

背景：同一 model + group 配了多个渠道时，`model.GetRandomSatisfiedChannel` 按权重每次独立随机，
同一会话的请求散落到不同渠道，上游 prompt cache 必然失效。项目已有「会话保持 / 渠道亲和性」
(settings → request policies → sessions and retries)，但内置规则只认 codex/claude CLI 的标识，
KV 缓存压测这类不带任何标识的请求无法使用。

改动：
- `setting/operation_setting/channel_affinity_setting.go`：`ChannelAffinityKeySource` 增加
  `Hash bool` (`json:"hash,omitempty"`)。对 gjson/header/context 提取出的值做 SHA-1 取前 16 位
  再作为亲和键，避免把 KB 级 prompt 原样写进缓存 key。
- `service/channel_affinity.go` `GetPreferredChannelByAffinity`：`value_regex` 校验通过 **之后**
  才哈希（value_regex 语义仍对原始文本生效）。
- `web/.../channel-affinity/types.ts`：`KeySource` 增加 `hash?: boolean`。
  UI 暂无勾选框，用规则的 JSON 编辑模式或 API 写入；`normalizeKeySource` 用展开运算符，字段不会丢。
- 新增 `service/channel_affinity_key_source_test.go`（5 个用例：不哈希保留原文、哈希后稳定/
  不含原文/固定 16 位、不同 prompt 不共用、value_regex 先于哈希、设置 JSON 往返保留字段）。

注意：
- `service` 包里 `TestObserveChannelAffinityUsageCacheByRelayFormat_UnsupportedModeKeepsEmpty`
  在整组运行时失败（全局用量统计缓存跨用例污染），单独运行通过，属既有问题，与本次改动无关。
- 亲和缓存用 `cachex.HybridCache`，多实例必须开 Redis，否则只有进程内缓存。

语义要点：亲和键取哪个字段 = 决定命中域。字段越靠前越稳定 → 命中率高但流量集中在单渠道；
想兼顾分散就让压测用多个不同前缀（数量 ≥ 渠道数）。

## 会话亲和在高并发下的既有隐患（读码确认，未改动）

- `pkg/cachex/hybrid_cache.go:80-129`：开启 Redis 后 Get/Set 全部直连 Redis，**内存层完全不参与读**，
  即「HybridCache 名不副实」。亲和开启后每个请求 ≈ 4 次 Redis 操作（读绑定 1 + 成功回写 1 +
  用量统计 Get/Set 各 1）。
- `service/channel_affinity.go:846-893` `observeChannelAffinityUsageCache`：对统计条目做
  「加锁 → Get → Set」的读改写，锁按 entryKey 哈希落到 `[64]sync.Mutex` 之一。同一 prompt 压测时
  entryKey 相同 → 所有请求串行在同一把锁上，且锁内还有 2 次 Redis RTT，是最硬的并发瓶颈。
- `service/channel_affinity.go:730-756` `RecordChannelAffinity` 每次成功都无条件覆盖绑定（last-write-wins）。
  渠道 429 触发重试迁移时，绑定会来回跳，命中率反而崩塌。
- `service/channel_affinity.go:618-623` / `752-755`：缓存操作失败按请求打 `common.SysError`，
  Redis 抖动时会造成日志风暴。
- `setting/config/config.go:42-70` 更新配置持 `ConfigManager.mutex` 原地改结构体，但
  `operation_setting.GetChannelAffinitySetting()` 返回裸指针、读方不加锁 → `Rules` 切片头存在数据竞争。
- Redis 模式下 `MaxEntries` 不生效（`HybridCache.Capacity()` 直接返回 0），缓存条数只受 TTL 约束。

## 正常使用场景的命中率优化结论

- 命中率只取决于「同一段前缀的连续请求是否落同一上游账号」，与渠道分配是否均匀无关。
- 键的最优粒度是**用户 ID**（`context_int id`）：比会话 ID 粗一层，同一用户多个会话共享同一账号，
  长 system prompt 可跨会话命中；再粗不会提高命中率，只会集中负载。
- 规则顺序敏感：`GetPreferredChannelByAffinity` 顺序遍历、第一条匹配即返回，具体规则必须排在兜底规则前。
- TTL 对齐并略长于上游缓存寿命（OpenAI 1800–3600，Anthropic 5min 缓存 300 / 1h 缓存 3600）；宁长勿短。
- 渠道侧三件事优先级高于规则本身：拆多 Key（多 Key 轮询会换账号=换缓存域）、优先级分层减少随机面、
  检查参数/请求头覆盖模板不要注入时间戳等动态值。

## Kimi 场景的关键约束（读码确认）

- 用户实际模型是 `kimi-k3`，不匹配内置两条 CLI 规则的 `^gpt-.*$` / `^claude-.*$`，那两条对他完全无效，
  真正生效的只有 `default-by-user`（`^.*$` + 用户 ID）。
- `relay/channel/openai/usage.go:31-43`：Moonshot 的 `usage.cached_tokens`（以及流式 `choices[].usage.cached_tokens`）
  **只在 `case constant.ChannelTypeMoonshot` 分支里**被提取到 `PromptTokensDetails.CachedTokens`。
  渠道若配成通用 OpenAI 类型，`usage.cached_tokens` 会被丢弃 → 会话亲和的「上游缓存命中统计」恒为 0，
  容易误判成亲和没生效。`ChannelTypeOpenAI` 分支只解析 llama.cpp 的 `timings.cache_n`。
- `relay/channel/moonshot/adaptor.go:103-106`：kimi-k3 的 `/v1/responses` 是原生透传，其他模型上游会拒。

### 会话级（而非用户级）亲和键

- 用户 ID 粒度太粗：单用户高并发会打满一条渠道并触发 429。
- 已验证可用：`gjson` 路径 `messages.#(role=="user").content` + `hash: true`
  —— 取首个用户消息，同一会话后续轮次键不变，不同会话可分散。GJSON 的 `#(...)` 查询在
  `gjson.GetBytes` 下正常工作（已实测：`messages.#(role=="user").content` → 首个匹配内容）。
- 用例：`TestGetPreferredChannelByAffinity_FirstUserMessageKey`（`service/channel_affinity_key_source_test.go`）。
- 边界：同一会话内的高并发仍会集中到一条渠道，这是缓存按账号隔离决定的，配置无法绕开。
