## 重试时排除已试过的渠道（上游 429 必定换渠道）

问题：上游返回 429 后判定为 retry，但选渠道时不参考 `use_channel`，同一优先级层里可能再次抽到
刚失败的那条渠道；两条同优先级渠道时重试预算只有 1 次（tierCount），抽错就直接把 429 返回给用户。

改动：
- `dto/channel_constraints.go`：新增 `FilterExcludeChannels` + `ChannelFilter.ChannelIDs`。
- `model/channel_constraint.go`：加入 `filterEvalOrder`，`channelMatchesFilter` 里用
  `!slices.Contains(filter.ChannelIDs, ch.Id)` 判定。
- `model/channel_cache.go`：`GetRandomSatisfiedChannel` 抽出 `candidatesFor`，当排除把候选清空时
  （`filterCandidateIDs` 返回 `emptiedBy == FilterExcludeChannels`）回退到不带排除的过滤，
  避免把上游 429 替换成"无可用渠道"的 503。
- `service/channel_select.go`：`RetryParam.ExcludeChannelIDs`；`CacheGetRandomSatisfiedChannel`
  用 `slices.Clone` 复制 filters 后追加排除过滤器（不改调用方的切片）。
- `controller/relay.go`、`relay/responses_websocket.go`：每次 retry>0 时从 `use_channel` 解析出
  已用渠道 ID 填进 `RetryParam`，覆盖 HTTP 与 Responses WebSocket 两条重试链路。

测试：
- `model/channel_constraint_test.go` 增 3 个表驱动用例（exclude 保留其余 / 全部被排除时报 kind / 无关候选不受影响）。
- 新增 `model/channel_cache_exclude_test.go`：排除后必定选另一条；全部排除时回退且有返回。
- 验证：affected 包 `go build` + `go vet` 通过；model 包全绿；controller 重试用例通过；
  relay 仅 `TestResponseModelHandlersCaptureBeforeConversion/claude` 失败（已在干净 HEAD
  7c53260fc 上复现，属既有问题）；service 仅既有的 usage-cache 用例失败。
- 另注：`controller` 整包测试会卡在 `TestOAuthBindIgnoresLegacyGitHubUsernames`（既有 hang，10 分钟超时）。

## 429 不计入重试预算

- 需求：任何非 2xx 都切渠道重试（默认就是，`AutomaticRetryStatusCodeRanges = 100-199,300-599`），
  但 429 应"直接换渠道、不消耗重试次数"，渠道并发 429 维持原有专门逻辑。
- `model/channel_satisfy.go`：抽出 `satisfiedCandidates`，`MaxConcurrencyRetryProbes` 改为复用它，
  新增 `RetryChannelCount`（返回过滤后的候选渠道数）。
- `controller/relay.go` + `relay/responses_websocket.go`：overrun 分支里若 `StatusCode == 429`，
  把 `switchBudget` 提到候选渠道数（`max(RetryChannelCount, tierCount)`），配合已实现的渠道排除，
  可以保证每条渠道都试一次再返回 429。
- 验证：build/vet 通过，`model` 与 controller 重试用例通过。

## 渠道 429 冷却（区分网关并发 vs 上游配额）

两种 429 在代码里本就分得开：网关并发闸门是 `types.ErrorCodeConcurrencyLimit`（由渠道
`MaxConcurrentRequests` 触发），上游 429 是真实状态码。冷却只针对后者。

- `common/constants.go`：`UpstreamQuotaCooldown = 60s`、`UpstreamRateLimitCooldown = 3s`。
- `model/channel_cooldown.go`（新）：进程内 `sync.Map[channelID]time.Time`，
  `MarkChannelCooldown`（只延长不缩短）/ `ChannelCooling` / `ClearChannelCooldown` /
  `dropCoolingChannels`（全部冷却时返回原列表，避免 503）。
- `model/channel_cache.go`：候选过滤后跳过冷却渠道；`CacheUpdateChannel` 清冷却。
- `service/channel_cooldown.go`（新）：`Upstream429Cooldown` 按错误文案关键字
  （quota/insufficient/billing/credit/balance）区分配额（60s）与限流（3s）。
- `service/channel_select.go`：亲和绑定指向冷却渠道时视为不可用 → 解绑 → 重新选，
  否则会话会一直回到吃 429 的渠道。
- `controller/relay.go`、`relay/responses_websocket.go`：上游 429 时打冷却标记
  （显式排除 `ErrorCodeConcurrencyLimit`）。
- 测试：`model/channel_cooldown_test.go`、`service/channel_cooldown_test.go` 通过。

## 大前缀 TTFT/TPM 压测脚本

- `tools/ttft_tpm_probe.py`：仅标准库。固定一个约 60k token 的前缀 → 预热两次建立上游缓存 →
  多轮并发（默认 20×6）复用同一前缀发流式请求，统计 TTFT p50/p95/max、cached 占比、实际 TPM。
- 用途：区分「上游排队导致首字变慢」与「缓存没命中」。
- 关键事实（排查首字对不上时确认过）：网关 FRT 的计时起点是
  `middleware/distributor.go:136` 设置 `ContextKeyRequestStartTime`（选完渠道、发上游前），
  终点是 `relay/helper/stream_scanner.go:272` 收到第一行 SSE data；因此 FRT 不含鉴权/选渠道开销。
- 某次 68k 输入、cached 3.2k、无重试的请求：FRT 168s、总 341s，网关侧仅 211ms，
  上游请求 ID 时间戳比网关晚 1 秒 → 时间差全部在上游（排队/预填算力被切碎）。
- 实测（api.hzjingmu.cn，kimi-k3，流式）：91 tok 冷 = 6.3s；4.4k 冷 = 13.2s；同前缀第二次 = 1.9s、
  第三次 cached=4403 全命中 = 2.2s；4 路并发同前缀 = 1.5–6.1s。
  → 上游预填约 340–400 tok/s，命中后固定约 2s。68k 冷 × 390 tok/s ≈ 167s，与那条 168s 吻合。
  → 该上游 WAF 会拦 `Python-urllib` 默认 UA（403），脚本必须带普通 UA。
