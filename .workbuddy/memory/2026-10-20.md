## nginx 配置缺陷（8888 这层）

1. `chunked_transfer_encoding off` → SSE 无 Content-Length，只能 Connection: close 收尾，
   每条流式请求独占 TCP，失去 upstream/客户端 keepalive，易耗尽端口与 TIME_WAIT。
2. `proxy_next_upstream off` → 与 upstream 的 `max_fails=3 fail_timeout=30s` 冲突（该计数只在
   切换 server 时生效），任一台连接失败直接 502，不切换其余 3 台。
3. `proxy_connect_timeout 60s` 过长；后端 accept queue 满时表现为 SYN 重传后约 7–8s 才 502。
4. `client_body_buffer_size 10m` 在 `proxy_request_buffering off` 下无意义且浪费内存。
5. 空 `location = /50x.html {}` + `error_page 502` → 暴露 nginx 默认页，无法区分故障层。
6. access_log 用默认 combined，缺 `$upstream_addr`/`$upstream_status`/`$upstream_response_time`。

## 429 全渠道轮询改造（rc.254 之后）

需求：上游 429 时必须轮询同分组其它渠道，不能把 429 直接还给客户。

根因（两处）：
1. `GetRandomSatisfiedChannel` 的 `candidatesFor` 在「排除后为空」时回退到全量列表，
   重试因此可以重新选中刚被拒的渠道。
2. 选择被 `switchBudget` 限制，而预算来自 `RetryChannelCount`；若某次 filters 只留下 1 条候选，
   预算就是 1，试一次即止。

改动：
- `model/channel_cache.go` 新增 `PickChannelForSwitch` + `pickWeightedChannel` +
  `switchCandidatesLocked`：跨优先级层选择，排除过滤器按严格语义处理（排空返回 nil, nil，
  不回退），并复用原有权重平滑。DB 模式走 `pickChannelForSwitchFromDB`。
- `service/channel_select.go`：`RetryParam.SwitchAcrossTiers`；auto / 普通两个分支都接入。
- `controller/relay.go`：`upstream429` 判定提到前面，置 `SwitchAcrossTiers`；
  预算分支条件改为 `retry >= RetryTimes || upstream429`；跨层时清空 `TierOverride`。
  `getChannel` 失败时保留已有 `newAPIError`（不再用 503 覆盖 429）。
- `relay/responses_websocket.go`：同样的改动。

测试：`model/channel_switch_test.go` 3 个用例通过（3 个优先级全部轮询一次、排空返回 nil、
同优先级逐条走完）；model 包全绿，controller 重试用例通过，build/vet 通过。

### 补充：轮询与渠道并发数的关系

每个渠道的 `MaxConcurrentRequests` 可以不同（`dto.ChannelSettings`），并发计数在 `service`
层按节点独立维护。原 429 轮询完全不看它，会选到打满的渠道 → 触发网关自己的并发 429
（`ErrorCodeConcurrencyLimit`）→ 进入 2 秒等待窗口，打断轮询。

改动：
- `service/channel_concurrency.go` 新增 `ChannelConcurrencyRoom(id, limit)` 与
  `saturatedChannelsSkip(channel)`（用候选渠道**自己的**上限判断）。
- `model.PickChannelForSwitch` 增加 `skip func(*Channel) bool` 参数，由
  `dropSaturatedChannels` 实现：有余量的优先，全满时保留全量（宁可等待也不报无渠道）。
- 测试新增 `TestPickChannelForSwitchSkipsSaturatedChannels`。

注意：并发计数是**每节点**的（`AcquireChannelConcurrency` 注释已说明），多实例部署时
A 节点看不到 B 节点的负载，只保证不超本节点上限。

## rc.255 的遗漏：只有 429 走了跨层选择（rc.256 修复）

用户贴的 403 日志只到第 4 条「状态码命中重试规则」就结束，`use_channel` 单条。根因链：

1. rc.254/255 的预算分支用 `tier := switchProbe % tierCount` 设置 `TierOverride`，把第 2 次尝试
   锁在最高优先级层；
2. 该层只有刚失败的渠道，`GetRandomSatisfiedChannel` 的「排除后为空」回退把它放回来；
3. `SelectChannelForRequest` 末尾的 `ChannelSatisfiesFilters` 又因它在排除列表而拒绝 →
   返回 `NoAvailableChannel`；
4. `getChannel` 报错 → `break`，客户端拿到第一次的 403/429。日志不会有第 5 条，因为
   `BeginAttempt` 只在选到渠道后才写事件。

rc.255 只对 `upstream429` 置了 `SwitchAcrossTiers`，**403/5xx 仍走旧路径**。已改为：
`if decision.Action == "retry" && ErrorCode != ConcurrencyLimit { SwitchAcrossTiers = true }`，
并把预算条件从 `if upstream429` 改为 `if retryParam.SwitchAcrossTiers`（预算 = 渠道数）。
HTTP 与 WebSocket 两条链路同步。build/vet 通过，model/controller/service 关键用例通过。

## 日志异步化（不丢，用于对账）

现象：一个渠道报错后，其它渠道也变慢。根因之一是 `RecordErrorLog` / `RecordConsumeLog` 在请求

## 冷却覆盖全部渠道级失败（rc.259）

原则：单请求代价 = 失败耗时 × 被撞的渠道数。无冷却时，一条坏渠道会让**每个**后续请求
重复支付这笔成本；N 条渠道同时坏，代价乘 N。因此冷却必须覆盖所有「渠道级失败」，
而不只是 429。

| 状态 | 冷却 | 说明 |
|---|---|---|
| 429 配额类 | 60s | 原有 |
| 429 限流类 | 3s | 原有 |
| 5xx（500/502/503/504） | 15s | rc.258 新增 |
| **402 余额不足** | 60s | rc.259，同配额语义 |
| **403 风控/权限** | 30s | rc.259，`UpstreamForbiddenCooldown` |
| **无状态码（连接失败）** | 15s | rc.259，`StatusCode <= 0` |
| 网关并发 429 | 1s | 原有，独立等待窗口 |

注意：`DoRequestFailed` 多数情况带 500，已被 5xx 分支覆盖；dial 失败可能 `StatusCode<=0`，
故单独兜底。本地错误（计费 403、读 body 失败）带 SkipRetry，不进入冷却分支。

## 关键认知修正：错误日志是「单次失败快照」，不是请求结果

用户多次看到「429 后日志停在第 4 条」以为没切渠道。实际机制：

- `ProcessChannelError` 在**每次失败时立刻**写一条错误日志，`other.request_policy` 是那一刻的
  事件快照，后续 attempt 不会回填；
- 重试成功后另有**一条消费日志**，里面才有完整的 `选择渠道 → 请求已完成` 事件。

所以「日志停在 retry_status_matched」不代表没切。判据：同 request_id 是否存在消费日志、
以及请求总耗时是否远超首条日志里的 attempt 耗时。第 4 条文案只显示「命中重试规则」，
未渲染 `decision.action`（retry/stop），是误读的主要来源。

## 重试分组解析 + 诊断日志（rc.260）

`pickChannelForSwitch` 之前直接用 `param.TokenGroup`，而亲和与预算都用 `UsingGroup`；
分组映射下两者不同会误报「无可用渠道」。现改为先试 `UsingGroup`、再试 `TokenGroup`。
并在两者都找不到时打系统日志（`logger.LogWarn`，进 docker logs）：

```
retry switch found no channel: group=... model=... total_candidates=N remaining=0 tried=[...]
```

`total_candidates=0` 说明分组/模型对不上；`remaining=0` 说明该请求已经把渠道试完——
这两种情况性质完全不同，靠这条日志一次就能区分。

## 冷却改指数退避（rc.261）

问题：窗口限流（如 `Inflight Batchsize limit`）需要等数分钟，但固定 3 秒冷却意味着
**每 3 秒就放一个请求去撞一次**，永远在「撞→冷却→再撞」循环。用户明确指出这点。

改动：
- `model/channel_cooldown.go`：存储从 `time.Time` 改为
  `channelCooldownEntry{until, strikes, lastAt}`；新增
  `MarkChannelCooldownBackoff(channelID, base, limit)` 与
  `cooldownBackoffDuration(base, limit, strikes)`（每次连续失败翻倍、封顶）。
- `NoteChannelHealthy(channelID)`：请求成功后清零 streak（在
  `MarkRequestPolicySuccess` 里调用），偶发失败不会累积成长冷却。
- 10 分钟无失败自动重置 streak（`channelCooldownStrikeReset`）。
- `ChannelCooling` 不再删除过期记录，改为只读 `until`，以便 strike 连续累积。
- 各类型 base / 上限：
  | 类型 | base | 上限 |
  |---|---|---|
  | 429 限流 | 3s | 60s |
  | 429 配额 | 60s | 300s |
  | 5xx | 15s | 120s |
  | 403 | 30s | 300s |
  | 402 | 60s | 300s |
  | 连接失败 | 15s | 120s |

测试：`model/channel_cooldown_backoff_test.go` 三个用例通过（翻倍与封顶、连续失败延长、

## action 扩展为三值：retry_no_cooldown（rc.269）

用户要求"不冷却只切渠道"。action 三值：
- `retry`：冷却（base→max 指数）+ 切渠道；
- `retry_no_cooldown`：**不冷却** + 切渠道（渠道立刻回池，仅本请求切走）；
- `cooldown_only`：冷却 + 快速失败。

实现：`Upstream429Cooldown` 命中 `retry_no_cooldown` 返回 0，`controller/relay.go`
冷却处对 base<=0 跳过 `MarkChannelCooldownBackoff`；校验放行该 action 且免 base 校验。
trade-off 已告知：渠道持续限流时每个新请求会先撞它一次（多付一个失败往返）。

测试：校验放行 + 命中匹配（inflight batchsize → retry_no_cooldown）通过；
service/middleware/model 回归与基线一致（6 个既有 Windows 噪音失败，无新增）。
前端描述 i18n 更新（三种 action 说明），locale 清理了 guard 误写的 null 条目。

**配置示例（用户场景）**：

[{"match": ["token rate limit", "rate limit exceeded"], "action": "retry_no_cooldown"}]
